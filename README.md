# npa-ingest

ตัวดึงข้อมูลทรัพย์ NPA และประกาศขายทอดตลาด — Phase 1 ของ NPA Deal Platform

## หลักการออกแบบ 4 ข้อ

**1. Raw-first** — เก็บ HTML ดิบก่อน parse เสมอ
เวลา parser เก่งขึ้น (และมันจะเก่งขึ้นแน่นอน) คุณ `--reparse` จากของเดิมได้เลย
ไม่ต้องกลับไปรบกวนเว็บต้นทาง และไม่เสียข้อมูลที่วันแรกยังไม่รู้ว่าจะใช้

**2. Append-only snapshot** — ห้าม UPDATE ทับ
ประกาศเดียวถูกนัดขายหลายรอบ ราคาลดลงเรื่อย ๆ ถ้า upsert ทับ คุณจะเหลือแค่ราคาล่าสุด
และเสียข้อมูลที่มีค่าที่สุดในโปรเจกต์นี้ไป คือ **เส้นทางการลดราคาแต่ละรอบ**

**3. แยก discover / fetch / parse** — เว็บเปลี่ยนโครงสร้างเมื่อไหร่ แก้แค่ `parse()`

**4. PDPA by default** — ชั้น snapshot สะอาดตั้งแต่แรก
raw เก็บได้แต่ต้อง auto-purge ใน 30 วัน ไม่มี RLS policy ให้ใครอ่าน และห้าม expose ผ่าน API

## โครงสร้าง

```
schema.sql                  ตาราง 4 ชั้น: raw → snapshot → identity → observability
src/core/http.py            encoding TIS-620, rate limit, retry, robots.txt
src/core/pii.py             ตัดชื่อคู่ความ/เลขคดี/บ้านเลขที่/เลขบัตร
src/core/db.py              psycopg3 + dedupe ด้วย content_hash
src/core/base_adapter.py    interface ที่ทุก source สืบทอด
src/adapters/led_auction.py adapter แรก (มี TODO ที่ต้องเติมหลัง probe)

tools/probe.py              สำรวจหน้าเว็บก่อนเขียน parser
.github/workflows/ingest.yml cron 05:00 เวลาไทย
```

### การแยกอำเภอกับจังหวัด — สองปัญหาซ้อนกัน

**ปัญหาที่ 1: ชื่อโครงการมีจุลภาคอยู่ข้างใน**

```
โครงการลุมพินี วิลล์ อ่อนนุช 46 เอ,บี สวนหลวง, กรุงเทพมหานคร
```

เช่น `โครงการสินเพชร นนทบุรี บางบัวทอง, นนทบุรี`

**ปัญหาที่ 2: ชื่ออำเภอกับปัญหาภาษาไทยไม่มีช่องว่าง**

BAM เขียนชื่อทรัพย์ติดกับชื่ออำเภอ เช่น `หมู่บ้านมนวดีบางบัวทอง, นนทบุรี`

**ยอมให้ว่างดีกว่าเดาผิด** เพราะข้อมูลตำแหน่งที่ผิดทำให้การวิเคราะห์โซนพังทั้งระบบ

## ข้อควรระวัง

- **อย่าเร่ง rate limit** ตั้งไว้ 3 วินาที/request และดึงวันละครั้งพอ เว็บราชการล่มง่ายและโดนบล็อก IP แล้วจบ
- **ใส่อีเมลจริงใน `USER_AGENT`** (`src/core/http.py`) เผื่อผู้ดูแลระบบต้องการติดต่อ ดีกว่าโดนบล็อกเงียบ ๆ
- **อย่าปิด `assert_clean()`** ถ้ามันระเบิด แปลว่า parser ดึง PII ติดมาจริง ต้องแก้ parser ไม่ใช่ปิด assertion
- **`rows_new` เป็น 0 ไม่ได้แปลว่าพัง** อาจแปลว่าไม่มีประกาศใหม่ ดูที่ `pages_fetched` ประกอบ

## ชั้นประเมินมูลค่าอนาคต (migration 003)

ตอบคำถาม "ทรัพย์นี้มีอนาคตดีไหม" ด้วยหลักฐานย้อนหลัง ไม่ใช่แบบจำลองที่เดาเอง

**วิธี: difference-in-differences**

```
uplift จริง = (ราคาโซนใกล้เปลี่ยนไปกี่ %) − (ราคาโซนควบคุมเปลี่ยนไปกี่ %)
```

โซนควบคุมคือแถบ 2–8 กม. ในจังหวัดเดียวกัน ถ้าไม่หัก คุณจะเอาเงินเฟ้อทั้งเมือง
มานับเป็นผลงานของถนน ซึ่งทำให้ประเมินสูงเกินจริงเสมอ

**ผลลัพธ์เป็นช่วง 3 ฉาก ไม่ใช่ตัวเลขเดียว**

| | ที่มา |
|---|---|
| bear | p25 ของ uplift × โอกาสโครงการเกิดจริง × (1 − ค่าปรับความเสี่ยง) |
| mid | p50 ของ uplift ปรับเหมือนกัน |
| bull | p75 ของ uplift ปรับเหมือนกัน |

**โอกาสโครงการเกิดจริงถ่วงเข้าไปตรง ๆ** — โครงการขั้นผลการศึกษาให้ 20%
ขั้น พ.ร.ฎ. ให้ 75% ค่าเหล่านี้เป็นค่าตั้งต้น ต้องแทนที่ด้วยค่าจริงจาก
`v_stage_base_rates` ทันทีที่มีโครงการในระบบ 20 โครงการต่อประเภท

**Survivorship bias คือกับดักใหญ่ที่สุด** — โครงการที่สร้างเสร็จเห็นชัด
แต่โครงการที่ถูกยกเลิกมองไม่เห็น ต้องบันทึก `lifecycle_status` เป็น
`stalled`/`cancelled` ด้วย ไม่งั้น uplift จะสูงเกินจริงทุกครั้ง

**Confidence มาจากปริมาณหลักฐาน ไม่ใช่ความแรงของตัวเลข**
เห็น uplift 60% จากตัวอย่าง 3 ดีล = `low` ไม่ใช่ `high`

**ตรวจความแม่นย้อนหลังเสมอ** — ตาราง `forecast_outcomes` เก็บผลจริงตอนทรัพย์ถูกขาย
ถ้าไม่มีตารางนี้จะไม่มีวันรู้ว่าโมเดลใช้ได้หรือเปล่า

ดู `queries/corridor_price_change.sql` สำหรับวิเคราะห์ราคาตามแนวโครงการ

## วงจรพัฒนาโมเดล (migration 004)

โมเดลจะแม่นขึ้นตามข้อมูล แต่ต้องมีระบบกันไม่ให้มัน **แย่ลงโดยไม่มีใครรู้**

**แยกการเปลี่ยนแปลงเป็นสองประเภท**

| | ตัวอย่าง | ทำอัตโนมัติ? | version |
|---|---|---|---|
| A. Parameter refresh | เส้นโค้ง uplift, base rate อัปเดตตามข้อมูลใหม่ | ได้ รายเดือน | patch |
| B. Structure change | เพิ่มตัวแปร เปลี่ยนสูตร เปลี่ยนวิธีถ่วงน้ำหนัก | **ไม่ได้** ต้อง backtest + คนอนุมัติ | minor/major |

การปล่อยให้ B เกิดอัตโนมัติคือจุดที่ระบบพังเงียบ ๆ

**Point-in-time snapshot กัน data leakage**
การพยากรณ์ ณ วันที่ D ใช้ได้เฉพาะเส้นโค้งที่ `as_of_date <= D` ถ้า backtest
ใช้เส้นโค้งที่คำนวณจากข้อมูลอนาคต ผลจะดูดีเกินจริงเสมอ แล้วคุณจะปล่อย
โมเดลห่วยขึ้น production ด้วยความมั่นใจเต็มเปี่ยม

**การพยากรณ์เป็น append-only** มี trigger ห้าม UPDATE ถ้าแก้ค่าเก่าได้
จะประเมินความแม่นย้อนหลังไม่ได้เลย

**ตัวชี้วัดที่สำคัญที่สุดคือ band_coverage ไม่ใช่ error**
ใช้ p25-p75 เป็นช่วง ค่าจริงควรตกในช่วงราว 50%
- สูงกว่ามาก = ช่วงกว้างจนไร้ประโยชน์
- ต่ำกว่ามาก = มั่นใจเกินจริง อันตรายกว่า

**Champion / challenger** โมเดลใหม่รันคู่ขนาน (`is_shadow = true`) ไม่แสดงให้ลูกค้าเห็น
จนกว่าจะผ่านเกณฑ์ใน `promotion_criteria` ที่ประกาศไว้ล่วงหน้า

> ห้ามแก้เกณฑ์หลังเห็นผลแล้ว เพื่อให้โมเดลที่อยากใช้ผ่าน

**เลื่อนขั้นด้วยมือเสมอ** แม้ผ่านเกณฑ์ทุกข้อ เพราะตัวเลขจับไม่ได้ว่าโมเดลใหม่
ทำพลาดในเคสสำคัญหรือเปล่า

```bash
python src/model_ops.py monthly                          # รายงานสุขภาพโมเดล
python src/model_ops.py drift                            # ตรวจเส้นโค้งผิดปกติ
python src/model_ops.py promote --version 0.2.0 --approved-by "ชื่อคุณ"
```

**ความจริงที่ต้องยอมรับ:** horizon 5 ปี จะรู้ผลจริงในอีก 5 ปี ช่วง 2 ปีแรก
confidence จะเป็น `low` เกือบทั้งหมด — นั่นถูกต้องแล้ว ไม่ใช่ข้อบกพร่อง
ให้ใช้ horizon 12/24 เดือนเป็นสัญญาณเตือนล่วงหน้าว่าโมเดลเอนไปทางไหน

## แหล่งราคาและความน่าเชื่อถือ (migration 005)

**ไทยไม่มีฐานข้อมูลราคาซื้อขายรายแปลงที่เปิดสาธารณะ** ราคาโอนอยู่ที่กรมที่ดิน
แต่ไม่เปิดรายแปลง และมักถูกแจ้งต่ำกว่าจริงเพื่อลดค่าธรรมเนียมกับภาษี
ราคาปิดประมูล LED จึงเป็นราคาธุรกรรมจริงรายทรัพย์ที่ดีที่สุดที่หาได้

| Tier | แหล่ง | เงินจริง | ใช้คำนวณ uplift |
|---|---|---|---|
| A_auction_close | ราคาปิดประมูล LED | ใช่ | ได้ — แกนหลัก |
| A_own_deal | ดีลที่เราปิดเอง | ใช่ | ได้ — น้อยแต่แม่นสุด |
| B_reic_aggregate | REIC รายจังหวัด/ไตรมาส | ใช่ | ได้ — เป็นชุดควบคุม |
| C_gov_appraisal | ราคาประเมินกรมธนารักษ์ | ไม่ | ไม่ได้ |
| D_asking | ราคาประกาศบนแพลตฟอร์ม | ไม่ | ไม่ได้ |
| E_npa_listed | ราคาตั้งขาย NPA ธนาคาร | ไม่ | ไม่ได้ |

มี trigger บังคับไว้ในฐานข้อมูลเลย — insert uplift ด้วย tier ที่ไม่ใช่เงินจริงจะ error

**ราคาประมูลใช้วัด uplift ได้ แม้จะต่ำกว่าราคาตลาด**
DiD วัด *การเปลี่ยนแปลง* ไม่ใช่ *ระดับ* ตราบใดที่อัตราส่วนลดคงที่ ส่วนลดจะหักล้างกันเอง
แต่ต้องทดสอบสมมติฐานนี้จริง ๆ ด้วย `v_spread_stability` — ถ้า CV เกิน 0.20
แปลว่าส่วนลดไม่คงที่ และตัวเลข uplift กำลังปนเปื้อน

**การแปลงเป็นมูลค่าตลาดต้องใช้ตัวปรับแยกต่างหาก** วัดได้ 3 ทาง
1. `resale_tracking` — ทรัพย์ที่ประมูลได้แล้วขายต่อ ให้ส่วนต่างจริง (แม่นสุด รอ 1-2 ปี)
2. ดีลที่เราปิดเอง เทียบราคาประมูลในเขตเดียวกัน
3. REIC ราคาเฉลี่ยต่อหน่วยรายจังหวัด (หยาบ แต่ใช้ได้ทันที)

เริ่มจากทาง 3 แล้วแทนที่ด้วยทาง 1 เมื่อข้อมูลพอ

```sql
select sync_auction_prices();     -- ดึงราคาปิดประมูลเข้า price_observations
select * from v_spread_stability; -- เช็คว่าส่วนลดคงที่พอจะใช้ DiD ไหม
```

## เว็บแสดงผล

รันบนเครื่องตัวเอง ไม่ต้องแตะคลาวด์

```powershell
pip install -r requirements.txt
python src\web.py
```

ถ้ายังไม่ได้ตั้ง `DATABASE_URL` เว็บจะเข้าโหมดตัวอย่างอัตโนมัติและบอกเหตุผลบนหน้าจอ
ไม่ต้องตั้ง env อะไรทั้งนั้น พอตั้ง `DATABASE_URL` ใน `.env` แล้วมันจะสลับไปใช้ข้อมูลจริงเอง

บังคับโหมดตัวอย่างทั้งที่มีฐานข้อมูลแล้ว:

| shell | คำสั่ง |
|---|---|
| PowerShell | `$env:DEMO_MODE = "1"` |
| Command Prompt | `set DEMO_MODE=1` |

เปิด http://127.0.0.1:8000 · หน้าสุขภาพระบบที่ /health

**ทำไมยังไม่ใช้ Next.js** — เฟสนี้คนใช้คือคุณคนเดียว สิ่งที่ต้องการคือเห็นข้อมูลเร็วที่สุด
ไม่ใช่ระบบที่สวยที่สุด ค่อยย้ายตอนเปิดให้คนนอกใช้ (Phase 3)

| เขต/อำเภอ | รายการมาจากข้อมูลจริงที่มีในฐาน ไม่ใช่ลิสต์ตายตัว |
| ประเภททรัพย์ | |
| ราคาตั้งแต่ / ไม่เกิน | |
| แหล่ง (สถาบัน) | |
| เกรดขั้นต่ำ | |

**อำเภอสัมพันธ์กับจังหวัดอัตโนมัติ** เลือกจังหวัดแล้วรายการอำเภอจะกรองให้ทันที
ทำด้วย JavaScript ในหน้า ไม่รีเฟรช จะได้ไม่เสียค่าที่กรอกไว้ช่องอื่น

**ช่องราคาว่างได้** ถ้าประกาศพารามิเตอร์เป็น `float` FastAPI จะปฏิเสธทั้งคำขอ
เมื่อฟอร์มส่ง `max_price=` มา (ซึ่ง HTML ส่งเสมอ) จึงต้องรับเป็นสตริงแล้วแปลงเอง

**ยังไม่มีตัวกรองตำบล/แขวง** เพราะหน้าค้นหาของ BAM ไม่ส่งข้อมูลตำบลมา
มีแค่ระดับอำเภอ ถ้าต้องการต้องเข้าหน้ารายละเอียดทีละรายการ ซึ่งเป็นคนละงาน

### การกรองทำที่ฐานข้อมูล ไม่ใช่ในหน่วยความจำ

เดิมโค้ดดึงมา 500 แถวแล้วค่อยกรองใน Python ซึ่ง **ผิด** เพราะทรัพย์ที่เข้าเงื่อนไข
แต่อยู่นอก 500 แถวแรกจะไม่มีวันปรากฏ ตอนข้อมูลยังน้อยไม่เห็นปัญหา
พอโตเป็นหลักพันจะเห็นว่า "พบ 500 รายการ" ตลอดไม่ว่ากรองอะไร

ตอนนี้ย้ายไปทำที่ SQL ทั้งการกรอง การนับ และการแบ่งหน้า
ทดสอบกับ 2,144 รายการแล้วใช้เวลาไม่ถึง 0.2 วินาที

### เทียบราคาตลาด (migration 007)

หน้า `/compare` แสดงราคาประมูลเทียบราคาตลาดจาก 2-3 แหล่ง พร้อมวันที่อัปเดต

**ตัวเลขสองค่าที่ต้องแยกให้ขาด**

| | ความหมาย |
|---|---|
| ส่วนต่างดิบ | เทียบราคาปิดประมูลกับราคาตั้งขายตรง ๆ — สวยแต่หลอก |
| ส่วนต่างหลังปรับ | หักส่วนลดต่อรองออกจากราคาตั้งขายก่อน — ใกล้ความจริงกว่า |

ราคาบนเว็บประกาศขายคือราคา **ตั้งขาย** ยังไม่ผ่านการต่อรอง ถ้าเทียบตรง ๆ
คุณจะเชื่อว่าทรัพย์ประมูลถูกกว่าตลาด 45% ทั้งที่จริงอาจ 35% แล้วตั้งราคาขายต่อผิด

ค่าส่วนลดต่อรองตอนนี้เป็น **ค่าสมมติ 8%** อยู่ในตาราง `asking_haircut`
ต้องแทนที่ด้วยค่าจริงจากดีลที่ปิดเอง หน้าเว็บเตือนไว้ด้วยสีเหลืองแล้ว

**ความสดของข้อมูล** แถวที่เก่าเกิน 45 วันจะจางลงอัตโนมัติ

### เก็บข้อมูลเปรียบเทียบยังไงให้ไม่ผิดกฎ

เว็บประกาศขายส่วนใหญ่ห้ามดึงข้อมูลอัตโนมัติใน ToS และการทำสำเนาประกาศหรือรูป
คือการละเมิดลิขสิทธิ์ชัดเจน ระบบนี้จึงเก็บเฉพาะ **สถิติรวมรายเขต**
(มีกี่รายการ ราคากลางเท่าไหร่) ซึ่งเป็นข้อเท็จจริงเชิงตัวเลข ไม่ใช่การทำซ้ำเนื้อหา
และลิงก์กลับไปหน้าค้นหาต้นทางเสมอ

```bash
python tools/add_comp.py
```

กรอกมือ ใช้เวลาราว 3-4 นาทีต่อเขตต่อเว็บ ทำเดือนละครั้งต่อเขตโฟกัสก็พอ
ราคาตั้งขายไม่ได้เปลี่ยนรายวัน

> ชื่อเว็บใน `comp_sources` เว้นว่างไว้เป็น A/B/C โดยตั้งใจ
> ให้เติมเองหลังอ่าน ToS ของแต่ละเว็บแล้ว และถ้าเว็บไหนมี API
> หรือโครงการพันธมิตรสำหรับนายหน้า ให้ใช้ช่องทางนั้นแทนทุกครั้ง

### รูปจากต้นทาง (migration 013)

BAM ใส่ URL รูปไว้ในการ์ดตรง ๆ เก็บง่าย

```
https://bam-bo-fs-prd.bam.co.th/bam/asset-small/<uuid>-<index>.jpg
```

**เก็บแค่ URL ไม่ดาวน์โหลดมาเก็บ** ประหยัดพื้นที่ และไม่เป็นการทำสำเนางานของเขา
หน้าเว็บโหลดรูปจากต้นทางโดยตรง

**ไม่ไล่เดา index รูปอื่น** ถึงจะรู้ว่า `-1.jpg` `-2.jpg` มีอยู่จริง
การยิงลองทีละเลขคือการรบกวนเซิร์ฟเวอร์เขาโดยไม่จำเป็น
ถ้าอยากได้แกลเลอรีเต็มต้องเข้าหน้ารายละเอียด ซึ่งเป็นคนละงาน

**รูปอยู่ใน listing_snapshots ไม่ใช่ listing_images** เพราะรูปที่ต้นทางใช้
เปลี่ยนได้เมื่อเขาอัปเดตประกาศ จึงเป็นส่วนหนึ่งของสภาพประกาศ ณ เวลานั้น
ส่วน `listing_images` สงวนไว้สำหรับรูปที่เราถ่ายเอง

### แบ่งหน้าและ lazy loading — จำเป็น ไม่ใช่ของแถม

รูปใบละ 170-440 KB ถ้าแสดง 500 การ์ดในหน้าเดียวคือ **100+ MB ต่อการเปิดหนึ่งครั้ง**
ซึ่งพังทันทีบนมือถือ

- แบ่งหน้าละ 24 การ์ด (`PAGE_SIZE` ใน `web.py`)
- ทุกรูปมี `loading="lazy"` โหลดเฉพาะที่เลื่อนถึง
- `onerror` ซ่อนรูปที่โหลดไม่ได้ แทนที่จะโชว์ไอคอนรูปเสีย

### รูปภาพกับลิขสิทธิ์ (migration 006)

**รูปจากเว็บอื่นเป็นงานมีลิขสิทธิ์** ใช้ดูเองเพื่อวิเคราะห์เป็นเรื่องหนึ่ง
เอาไปแสดงในสินค้าที่ให้คนอื่นดูเป็นอีกเรื่องหนึ่ง ระบบจึงติดธง `usage_scope` ทุกรูป

| image_source | เผยแพร่ได้ |
|---|---|
| `own_survey` รูปที่เราถ่ายเอง | ได้ |
| `broker_authorized` ได้รับอนุญาตจากเจ้าของทรัพย์ | ได้ |
| `led_announcement` รูปแนบประกาศราชการ | ใช้ภายในก่อน |
| `bank_npa` รูปจากเว็บธนาคาร/AMC | ใช้ภายใน |
| `portal_listing` รูปจากเว็บประกาศขาย | ใช้ภายใน ห้ามเผยแพร่ |

รันด้วย `PUBLIC_MODE=1` เมื่อไหร่ เว็บจะซ่อนรูปที่ไม่มีสิทธิ์อัตโนมัติ
และขึ้นข้อความว่า "ซ่อนรูปไว้ N ใบ" แทนที่จะเงียบ ๆ

| shell | คำสั่ง |
|---|---|
| PowerShell | `$env:PUBLIC_MODE = "1"` |
| Command Prompt | `set PUBLIC_MODE=1` |

**ทางออกระยะยาวคือรูปของตัวเอง** ซึ่งคุณจะมีอยู่แล้วจากขั้นสำรวจทรัพย์
(โมดูล 8 shot list) รูปเหล่านั้นเผยแพร่ได้เต็มที่และดีกว่ารูปจากเว็บอื่นด้วย
เพราะเป็นสภาพปัจจุบันจริง ไม่ใช่รูปเก่าที่ถ่ายไว้ตอนตั้งขาย

ทรัพย์ที่ยังไม่มีรูปจะได้ placeholder ที่สร้างเป็น SVG ในเครื่อง
ไม่เรียกบริการภายนอก จึงใช้งานได้แม้ออฟไลน์และไม่มีปัญหาลิขสิทธิ์

### เรื่องลิงก์ไปหาทรัพย์

`src/core/source_links.py` คืนลิงก์พร้อมระดับความมั่นใจ 2 แบบ

| แบบ | ความหมาย | หน้าตาใน UI |
|---|---|---|
| `deep` | ลิงก์ตรงไปหน้าประกาศ | ปุ่มปกติ |
| `search` | ลิงก์ไปหน้าค้นหา + แสดงเลขอ้างอิงให้ก๊อป | ปุ่มขอบประ + มีลูกศร |

ตอนนี้ทุกแหล่งเป็น `search` เพราะยังไม่ได้ยืนยัน URL pattern จริง
**ลิงก์ที่พาไปหน้าค้นหาแล้วผู้ใช้กรองเอง ดีกว่าลิงก์ตรงที่ 404**
เมื่อ probe แล้วรู้ pattern ให้เติมใน `DEEP_LINK_PATTERNS` แล้วปุ่มจะเปลี่ยนเอง

นอกจากลิงก์ต้นทาง แต่ละทรัพย์ยังมี:
- **เปิดแผนที่** — ดูทำเลรอบข้าง
- **Street View** — ดูสภาพภายนอกโดยไม่ต้องขับรถไป คัดกรองรอบแรกได้เร็วมาก
- **LandsMaps** — ตรวจรูปแปลง ทางเข้าออก และราคาประเมิน

## ระบบสมาชิกผู้รับเหมา (migration 008)

**ลำดับที่ห้ามสลับ**

```
มี deal flow จริง → ผู้รับเหมาสมัครฟรี → พิสูจน์ว่ามีงานส่งให้จริง → ค่อยเก็บเงิน
```

ราคาในตาราง `contractor_plans` ตั้งเป็น **0 ทุกแผนโดยตั้งใจ**
ห้ามตั้งราคาก่อนรู้ว่าหนึ่ง lead มีมูลค่าเท่าไหร่จริง

**เก็บค่าสมาชิก ไม่ใช่หักเปอร์เซ็นต์จากงาน** เพราะความเสี่ยงหลักคือ leakage —
ผู้รับเหมากับลูกค้าเจอกันผ่านเราแล้วไปตกลงกันเองนอกระบบ ค่าสมาชิกเก็บล่วงหน้า
และไม่ต้องพิสูจน์ว่าใครปิดงานได้ ส่วนค่าคอมต่องานบังคับใช้ไม่ได้จริง
และจะผลักผู้รับเหมาที่ดีที่สุดออกจากระบบ

### เกณฑ์จับคู่

```sql
select * from match_contractors('<job_request_id>', 5);
```

คืนคะแนนพร้อม `reasons` แบบ JSON ที่อธิบายได้ทุกองค์ประกอบ ตามหลักการข้อ 1 ของโปรเจกต์

| องค์ประกอบ | น้ำหนัก | เหตุผล |
|---|---|---|
| พื้นที่ | สูงสุด 40 | ค่าเดินทางกินกำไร ผู้รับเหมาไม่ข้ามจังหวัดจริง โซนหลักได้เต็ม |
| ความชำนาญ | สูงสุด 35 + โบนัสระดับ strong/expert | ตรงกี่ % ของงานที่ต้องการ |
| ยืนยันตัวตน | 0–10 | ตรวจเอกสาร 6 · ลงพื้นที่ 10 |
| ผลงานจริง | ตามคะแนนและ overrun | จาก `job_outcomes` เท่านั้น |
| งบไม่ตรงช่วงที่รับ | −25 | ส่ง lead ที่เขาไม่รับคือทำลายความไว้ใจ |
| ไม่รับงานทรัพย์ยึด | −40 | ทรัพย์ยึดมักสกปรก มีของเดิมทิ้งไว้ ต้องถามตั้งแต่สมัคร |

ระบบเคารพโควตา lead ตามแผนอัตโนมัติ — คนที่ใช้ครบแล้วจะไม่ถูกส่งงานเพิ่ม

### เหตุผลที่แท้จริงที่อยากได้ผู้รับเหมาในระบบ

`v_quote_calibration` — ทุกใบเสนอราคาทำให้ตาราง `unit_costs` ของเราแม่นขึ้น
และ `actual_to_quote_ratio` บอกว่าราคาที่เสนอกับที่จ่ายจริงต่างกันเท่าไหร่

ผู้รับเหมาจึงไม่ใช่แค่ลูกค้า แต่เป็นแหล่งสอบเทียบของโมเดลประเมินราคา
ยิ่งมีผู้รับเหมาในระบบมาก การประเมินค่ารีโนเวทยิ่งแม่นกว่าคู่แข่ง

### รีวิวรับเฉพาะจากงานที่จบจริง

`v_contractor_performance` คำนวณจาก `job_outcomes` เท่านั้น ไม่มีช่องให้รีวิวลอย
กันทั้งรีวิวปลอมและรีวิวกลั่นแกล้ง แลกกับการที่ช่วงแรกจะยังไม่มีคะแนนเลย
ซึ่งยอมรับได้ เพราะคะแนนปลอมอันตรายกว่าไม่มีคะแนน

## แกลเลอรีรูป (migration 015)

หน้าค้นหาให้รูปมาใบเดียว แต่หน้ารายละเอียดของ BAM มี 15-20 ใบ

**ดึงแบบ lazy — เฉพาะตอนมีคนเปิดดูจริง**

```
เปิดหน้ารายละเอียดครั้งแรก  3.3 วินาที · ดึงรูปจากต้นทาง
เปิดครั้งต่อไป              0.07 วินาที · อ่านจาก cache
```

ถ้าดึงล่วงหน้าทุกทรัพย์คือ 3,400 request เพิ่ม ใช้เวลาเป็นชั่วโมง
แต่ทรัพย์ส่วนใหญ่ไม่มีใครเปิดดูเลย ต้นทุนจึงควรแปรผันตามความสนใจจริง

**บันทึกผลทุกครั้งแม้ไม่เจอรูป** (`gallery_fetch_log`) ไม่งั้นทรัพย์ที่ไม่มีรูป
จะถูกยิงซ้ำทุกครั้งที่มีคนกดเข้ามา

**ตรวจโดเมนก่อนยิงเสมอ** เคยพลาดยิงไปที่ Google Maps เพราะรับ URL ผิดตัวมา
ตอนนี้เช็คว่าต้องมี `bam.co.th/th/npa/property/` เท่านั้น

### ทำไมปิดลิงก์ต้นทางเป็นค่าเริ่มต้น

นี่ไม่ใช่เรื่องเทคนิคแต่เป็นเรื่องรายได้

```
โชว์ลิงก์  ผู้ซื้อสะดวก ตรวจสอบเองได้ น่าเชื่อถือขึ้น
          แต่เขาอาจติดต่อสถาบันเองแล้วเราไม่ได้ค่าคอม (leakage)

ซ่อนลิงก์  กัน leakage
          แต่ดูปิดบัง และผู้ซื้อตรวจสอบเองไม่ได้
```

ไม่มีคำตอบตายตัว ขึ้นกับว่าคุณเชื่อว่าความไว้ใจหรือค่าคอมสำคัญกว่า
จึงทำให้ปรับได้ตลอดเวลา

**admin เห็นลิงก์เสมอ** ไม่ว่าตั้งค่าไว้อย่างไร — เติม `?token=รหัสของคุณ`
ต่อท้าย URL หน้าไหนก็ได้ จะเห็นแบดจ์ "มุมมอง admin" กำกับ

### ตั้งค่าแยกรายสถาบัน

บางสัญญานายหน้ากำหนดว่า **ต้อง** ลิงก์กลับไปหน้าเจ้าของทรัพย์

```sql
update institutions set allow_source_link = true  where code = 'bam';   -- บังคับเปิด

```

### PDPA ในการเก็บ event

ไม่เก็บ IP ไม่เก็บ user agent เต็ม ไม่เก็บอะไรที่ระบุตัวได้

ข้อมูลระดับ event เก็บ 90 วันแล้วลบอัตโนมัติ เหลือแค่ยอดรวมรายวัน

## SAM ให้พิกัดจริงระดับแปลง

หน้ารายละเอียดของ SAM มีลิงก์แผนที่ที่ฝังพิกัดไว้ตรง ๆ

```html
<a href="show_map.php?lat=13.99566&lng=100.32616">
```

**นี่ดีกว่า geocode ทุกกรณี** เพราะ geocode ได้แค่จุดกึ่งกลางตำบล
ทรัพย์ทุกตัวในตำบลเดียวกันจึงซ้อนกัน ส่วนพิกัดจริงกระจายถูกต้อง

ผลทดสอบจริง

```
sam   parcel        18 ทรัพย์ | 18 จุดต่างกัน   ← ไม่ซ้อนเลย
bam   subdistrict   11 ทรัพย์ |  9 จุด
bam   district      23 ทรัพย์ |  4 จุด          ← ซ้อนกันหนัก
```

ระบบเก็บ `geo_precision = 'parcel'` ไว้ และ popup บนแผนที่จะบอกว่า
"พิกัดจริงของแปลง" ด้วยสีเขียว ต่างจากพิกัดที่ประมาณเอา

**โควตาการดึงกระจายทุกแหล่ง** ถ้าไม่กระจาย แหล่งที่ชื่อขึ้นก่อน (bam)
จะกินโควตาทั้งหมดจนแหล่งอื่นไม่ได้ทำเลยเป็นสัปดาห์

## ที่อยู่เต็มและพิกัดระดับตำบล (migration 016)

**ปัญหาที่แก้** หน้าค้นหาของ BAM ให้แค่ระดับอำเภอ ทำให้ทรัพย์ทุกตัวในอำเภอเดียวกัน
ได้พิกัดเดียวกันหมด แผนที่กลายเป็นหมุดซ้อนกันเป็นร้อยที่จุดเดียว
ซึ่งไม่ใช่แค่ดูไม่สวย แต่**สื่อความหมายผิด**ว่าทรัพย์กระจุกอยู่ตรงนั้น
ทั้งที่อาจอยู่คนละมุมอำเภอห่างกัน 10 กิโล

**หน้ารายละเอียดมีที่อยู่เต็ม** ในรูปแบบสม่ำเสมอ

```
ที่ตั้งทรัพย์ เลขที่ 64/81 ซอย 5 หมู่บ้านมนวดี ถนนวัดลาดปลาดุก, บางคูรัด, บางบัวทอง, นนทบุรี
                                                              ตำบล      อำเภอ     จังหวัด
```

ดึงพร้อมแกลเลอรีในคำขอเดียว ไม่เพิ่ม request

```bash
python src/enrich.py details --limit 200   # ดึงที่อยู่
python src/enrich.py geocode               # หาพิกัดระดับตำบล
```

ผลจริงจากการทดสอบ

```
ก่อน: 23 ทรัพย์ อยู่ที่ 4 จุด    (ระดับอำเภอ)
หลัง:  8 ทรัพย์ อยู่ที่ 7 จุด    (ระดับตำบล)
```

**เคล็ดในการ query Nominatim ระดับตำบล** ทดสอบแล้วสองแบบนี้ได้ผลดีที่สุด
- `city=<ตำบล>&state=<จังหวัด>` ตรงกับระดับตำบล/เทศบาลใน OSM
- free text ต้อง**ไม่**ใส่คำว่า "ตำบล" นำหน้า ไม่งั้นไปเจอสำนักงานที่ดินแทน

**ยังไม่แม่นระดับแปลง** แม้ได้ตำบลแล้วก็ยังเป็นจุดกึ่งกลางตำบล
ทรัพย์ในตำบลเดียวกันยังซ้อนกันอยู่ แต่ดีขึ้นมาก
ถ้าต้องการระดับแปลงจริงต้อง geocode จากที่อยู่เต็ม ซึ่งความแม่นขึ้นกับว่า
OSM รู้จักถนนนั้นไหม เป็นงานถัดไปถ้าจำเป็น

## เติมพิกัดและให้เกรด

รันหลัง ingest ทุกครั้ง

```bash
python src/enrich.py geocode   # หาพิกัดโซนที่ยังไม่มีใน cache
python src/enrich.py grade     # คำนวณเกรดทุกรายการ
python src/enrich.py all       # ทั้งสองอย่าง
```

**Geocoding ใช้ Nominatim (OpenStreetMap)** ไม่ต้องมี API key ไม่ต้องผูกบัตร
แลกกับกติกาที่ต้องเคารพ — 1 request/วินาที และห้ามยิงซ้ำสิ่งที่รู้แล้ว
โค้ดบังคับไว้ทั้งสองข้อ ผลเก็บถาวรใน `geo_cache` รันซ้ำแล้วจะขึ้น "ต้องหาพิกัด 0 โซน"

**ต้องกรองผลให้เหลือเฉพาะ `boundary/administrative`** ไม่งั้น Nominatim จะคืน
โรงไฟฟ้า บริษัทเหล็ก หรือร้านก๋วยเตี๋ยวที่ชื่อคล้ายกัน ซึ่งพิกัดเพี้ยนไปหลายกิโล
โดยที่ดูเหมือนถูกต้อง — เจอจริงตอนทดสอบทั้งสามแบบ

**ความแม่นระดับอำเภอเท่านั้น** พิกัดที่ได้คือจุดกึ่งกลางอำเภอ ไม่ใช่ตำแหน่งทรัพย์
บันทึกไว้ในคอลัมน์ `geo_precision` ทุกแถว

| ใช้ได้ | ใช้ไม่ได้ |
|---|---|
| จัดกลุ่มโซน · แสดงหมุดคร่าว ๆ · วิเคราะห์ระดับเขต | วัดระยะถึงสถานีรถไฟฟ้า · ตรวจแนวเวนคืน |

อย่างหลังต้องรอพิกัดจริงระดับแปลง ไม่งั้นจะได้คำตอบผิดที่ดูน่าเชื่อถือ
